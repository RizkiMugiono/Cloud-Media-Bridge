# Provider-specific handoff

Use cloud handoff MANIFEST or MCP provider_handoff with the exact proposed or prepared plan. It returns a SHA-bound native request draft, selected lifecycle, official references, provider-specific review items and no permission to dispatch. provider_parameters is part of the immutable plan and accepts only recognized non-secret fields. Unknown fields are refused.

RunPod Pods draft includes exact cloud tier, GPU count, data center and pinned image. RunPod Serverless uses a reviewed template, queue endpoint, selected pool and explicit worker limits. Modal uses the official server CLI with explicit GPU count and no automatic confirmation or unauthenticated ingress; its ingress region does not prove GPU placement. Vast Instances binds the exact offer and requires current offer validation. Vast Serverless requires verified template, endpoint and worker-group contracts. Lambda requires actual instance type, VM image ID and pinned installation recipe, not OCI image substitution, and separate termination permission. Existing HTTPS/SSH hosts retain external ownership; Kubernetes requires an exact cluster context, namespace, GPU resource and node labels, and independent node lifecycle reconciliation.

These are request drafts, not complete native production executors. The preserved direct RunPod/Vast adapter checks provider-observed ownership marker and actual running/stopped state, and never mutates unknown/shared resources. Production is gated. External executor must independently verify inputs, current native API and evidence and operate only after signed consent. No credentials are accepted in manifests. Sources: https://github.com/runpod/runpod-python/blob/main/runpod/api/ctl_commands.py ; https://modal.com/docs/cli/latest/server ; https://vast.ai/developers/api ; https://docs.lambda.com/api/cloud ; https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/ .

No default fallback GPU or destructive action is chosen. Some provider modes require further implementation, separate worker protocol and live verification. Do not interpret a complete draft or a signature as production readiness.

MCP `lifecycle_action` produces an exact action draft only when lifecycle advice indicates the selected trigger is due. A different observed terminal state is treated as unexpected rather than success. Stop, termination, suspension and scale-to-zero are not interchangeable. External drafts remain unexecuted and unverified; the trusted executor must check the actual provider identity and grant.
